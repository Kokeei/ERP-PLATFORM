# Règles de développement — ERP-PLATFORM

Ce projet doit être traité comme une application en production. Ces règles s'appliquent à toute intervention de Claude Code sur ce dépôt, sauf instruction explicite contraire de l'utilisateur pour une tâche ponctuelle.

## 1. Avant toute modification

- Analyser l'architecture existante avant de coder : identifier les fichiers, sections et fonctionnalités concernés et ceux qui pourraient être impactés.
- Ne jamais modifier un fichier sans comprendre son rôle. Ne pas réécrire inutilement du code existant. Préférer les modifications minimales et ciblées.
- Avant une fonctionnalité importante, présenter brièvement : (1) l'existant, (2) ce qui est proposé, (3) les fichiers concernés, (4) les risques de régression — puis attendre confirmation si le choix engage une décision d'architecture.

## 2. Travail par fonctionnalité

- Une branche dédiée par fonctionnalité : `feature/nom-fonctionnalite`, ou `fix/nom-du-bug` pour un correctif.
- **Fusion vers `main`** : l'utilisateur a autorisé la fusion (merge) directe de la branche de fonctionnalité vers `main` sans passer par une pull request GitHub, à chaque fois, jusqu'à nouvel ordre. Ceci ne dispense pas des vérifications de la règle 4 (tests + suite complète) avant la fusion.
- Commits petits, cohérents, explicites (`feat: …`, `fix: …`, `test: …`, `refactor: …`), une fonctionnalité par commit.

## 3. Tests obligatoires

- Toute fonctionnalité nouvelle est accompagnée de tests (cas nominaux, cas limites, erreurs/données invalides, droits/permissions si pertinent).
- Toute correction de bug a un test qui reproduit le bug avant la correction.
- **État actuel du projet** : dépôt 100% statique (`index.html`, `rh/index.html`), sans `package.json`, sans framework de test, sans linter, sans étape de build. Avant la première fonctionnalité soumise à ces règles, une infrastructure de test doit être proposée et validée avec l'utilisateur (ex. Playwright pour des tests de bout en bout sur l'app statique) plutôt que d'être ajoutée unilatéralement.

## 4. Non-régression

Après chaque modification : exécuter les tests de la fonctionnalité puis la suite complète, vérifier lint/formatage et le build si applicable. Ne jamais déclarer une fonctionnalité terminée sur la seule base que le code s'exécute sans erreur visible.

## 5. Ne jamais contourner un test

Interdit : supprimer/désactiver un test qui échoue, modifier une assertion pour le faire passer, masquer une erreur avec un try/catch inutile. Si un test casse, déterminer s'il s'agit d'une régression (à corriger) ou d'un changement de comportement voulu (à justifier avant d'adapter le test).

## 6. Qualité du code

Respecter les conventions déjà en usage dans le fichier concerné, séparer les responsabilités, réutiliser l'existant, nommer explicitement, éviter code mort/dupliqué/dépendances inutiles et solutions temporaires laissées en place.

## 7. Sécurité

Jamais de secrets/tokens/clés en dur ou dans Git. Ne pas contourner un contrôle d'accès. Vérifier les droits pour toute fonctionnalité touchant des données sensibles (ex. dossiers agents, paie).

## 8. Git

Avant chaque commit : vérifier les fichiers modifiés, le diff, l'absence de fichier sensible/inutile, et que les tests passent. Messages de commit explicites.

## 9. Documentation

Toute fonctionnalité importante met à jour la documentation utile (fonctionnement, paramètres, nouvelles dépendances, procédures particulières).

## 10. Rapport de fin de tâche

Avant de déclarer un travail terminé, présenter : fonctionnalité réalisée, fichiers modifiés, tests ajoutés, tests exécutés (commande, réussis/échoués), vérifications (lint/build/tests : OK/KO), risques éventuels. Ne jamais déclarer « terminé » si tests ou build échouent, sauf échec explicitement identifié et signalé.

## Contexte technique du dépôt

- `index.html` : portail d'accueil de la plateforme ERP (liens vers les modules).
- `rh/index.html` : module RH complet (single-file, HTML/CSS/JS vanilla, aucune dépendance externe hors Google Fonts). Contient : dossier agent, congés (workflow N+1/N+2/RH), paie (génération + contrôle Direction Financière), allaitement, formations, notations, maternité, moteur de workflow générique réutilisable, profils différenciés (RH/Agent/Responsable/Direction Financière) simulés côté client (pas d'authentification réelle).
  - `rh/agent-portal.js` : portail self-service de l'agent (nav à 15 entrées : Accueil, Mon profil, Mes absences, Mes demandes, Mes tâches, Mes documents, Ma rémunération, Ma carrière, Mes formations, Mes entretiens, Ma vie professionnelle, Notifications, Recherche RH, Maternité/parentalité, Aide & contact). L'accueil (`renderAgentDashboard`) affiche les vrais soldes de congés de l'agent (`a.soldes` : CP, CPA « ancienneté », CPP « parental »), sa date de prochain avancement (`a.prochainAvancement`), ses prochains congés (triés du plus proche au plus lointain) et, s'il est titulaire d'un mandat de représentation du personnel (`a.mandatActif`/`a.mandatType`/`a.heuresDelegationMensuelles` — CE, DP, CHSCT…), ses heures de délégation mensuelles.
- `ged/` : module GED (Gestion Électronique des Documents), brique transverse réutilisable par les autres modules de l'ERP.
  - `ged/ged-core.js` : couche données/logique, sans dépendance DOM (`StorageProvider` abstrait avec implémentation IndexedDB par défaut, modèle espaces/dossiers/documents/versions/corbeille/audit, droits, recherche). Réutilise l'identité et l'annuaire agents déjà en place côté RH (mêmes clés `localStorage` : `oph_rh_v1` et `oph_rh_v1_session`) plutôt que de dupliquer une session.
  - `ged/ged-ui.js` : widgets d'interface réutilisables (modale de dépôt drag & drop, panneau détail document) — utilisés à la fois par `ged/index.html` et par l'onglet « Documents » du dossier agent RH (vue RH/Responsable, distincte de l'onglet « Mes documents » du portail self-service agent).
  - `ged/index.html` + `ged/ged.css` : module GED autonome (arborescence espaces/dossiers, recherche, corbeille, journal d'audit).
  - `ged/RECETTE.md` : checklist de recette fonctionnelle.
  - Le module RH n'a plus de gestion de documents qui lui soit propre pour le dossier complet agent (vue RH/Responsable) : `rh/index.html` délègue à la GED (voir `renderDocumentsPane()`), y compris l'import unique des documents historiques pré-existants (métadonnées uniquement, sans fichier réel, marqués comme tels).
  - **Important** : comme le reste du dépôt, la GED tourne entièrement côté navigateur (pas de backend). Les contrôles de droits (`GED.can()`) et l'audit sont une simulation pédagogique, pas une sécurité serveur — un déploiement réel nécessiterait un backend appliquant les mêmes règles côté serveur.
- `achats/index.html` : module Achats & Finances, regroupant les cartes portail « Clients / Tiers », « Fournisseurs », « Marchés publics », « Commandes », « Factures » et « Budget » — une seule application plutôt que 6 silos, car ces domaines forment une vraie chaîne d'achat (tiers → marché → commande engageant une ligne budgétaire → facture qui la consomme au paiement). Directions réelles de l'OPH : `DIRECTIONS = ["SG","DFC","DCL","DCP"]`, chacune avec un code à 3 chiffres attribué par son rang dans ce tableau (SG=001, DFC=002, DCL=003, DCP=004 — `directionCode()`). Référentiel `tiers` unique (un même tiers peut être client et fournisseur). Le budget est géré annuellement (variable globale `budgetExercice`, sélecteur d'exercice en haut de l'écran Budget) avec une hiérarchie **compte parent / compte enfant** : `comptesParents` (compte comptable, ex. 2183, avec son propre plafond `montantLimite` par exercice) et `budgetLignes` = les comptes enfants, un par direction (`compteParentId` + `direction`), dont le code affiché est `compteParentId.code + directionCode` (ex. 2183001 pour le SG, 2183002 pour la DFC — `compteEnfantCode()`) : chaque direction dépense sur son propre sous-compte et ne peut jamais entamer le budget d'une autre sur le même compte comptable. Sur l'écran Budget, chaque compte parent affiche son plafond et le **total de ses comptes enfants** (recalculé en direct, jamais stocké, pour rester comparable au plafond) ; les comptes peuvent être créés un par un (« Compte parent » / « Compte enfant ») ou **injectés en masse** par collage d'une liste `code;libellé;montant SG;montant DFC;montant DCL;montant DCP` (une ligne par compte, upsert si le compte existe déjà pour l'exercice — `openImporterComptesModal()`) ; un nouvel exercice se crée en dupliquant tous les comptes parents/enfants de l'exercice source (`openNouvelExerciceModal()`). La DFC peut aussi déplacer des crédits d'un compte enfant à un autre via un virement (`virements`, action « Virement de crédits » réservée au rôle DFC, qui vérifie que le montant ne dépasse pas le disponible du compte source). L'engagé d'un compte enfant somme les commandes **et les marchés** qui le référencent (`ligneEngage()`) et le liquidé somme les factures non rejetées, càd facturées (`ligneLiquide()`) — ni l'un ni l'autre n'est stocké. `marches` (inchangé, une seule ligne budgétaire par marché). La présentation formelle du budget à l'EPRD, la préparation budgétaire en amont par chaque direction et les décisions modificatives (DM, jusqu'à deux par an) restent à spécifier (colonnes à venir) et ne sont pas encore implémentées. `commandes` et `factures` sont désormais composées de **lignes** (`lignes[]` : désignation, type Produit/Prestation, quantité, prix unitaire HT, remise % — applicable en masse sur plusieurs lignes cochées à la fois —, garantie en mois — 0 par défaut —, compte budgétaire), **chaque ligne pouvant être imputée sur un compte budgétaire différent** ; la TVA est calculée automatiquement par ligne (16 % pour un produit, 13 % pour une prestation) ; le montant total (HT/TVA/TTC) est recalculé et stocké à chaque enregistrement (`calcLignesTotal()`). Le numéro des BC et des factures est **généré automatiquement et non modifiable** (format AAMMJJ + index du jour sur 2 chiffres = 8 chiffres, `numeroAuto()`) ; la facture porte en plus un `numeroFournisseur` (référence externe saisie, celle imprimée sur la facture papier du fournisseur). Cycle du BC : Brouillon → En attente de visa → Visée (le service SML vérifie le BC et appose son visa) → Signée DG (signature électronique) → Envoyée (par mail, par le service émetteur) → Livrée (« service fait » constaté) → Clôturée. Cycle de la facture : À contrôler → Bon à payer (par le service émetteur, contrôle bloqué tant que le service fait n'est pas constaté sur le BC lié) → Mandatement → Payée, ou Rejetée à tout moment du contrôle DFC (motif obligatoire). Ces cycles ayant évolué au fil du développement, `migrate()` fait correspondre les anciens statuts stockés en `localStorage` (commande `Validée` ; facture `Reçue`/`Contrôlée`/`Validée`) à leur équivalent dans le cycle courant, pour qu'un BC/une facture créé(e) sous un ancien schéma ne reste pas bloqué(e) sur un statut qu'aucun bouton ne permet plus de faire progresser. Une facture est rattachée soit à une commande (`commandeId`), soit à un marché (`marcheId`), jamais les deux ; elle peut porter une pénalité au tiers (`penaliteMontant`/`penaliteMotif`, montant net à payer = montant TTC − pénalité) et être justifiée par un **certificat administratif** (`certificatsAdministratifs`, numérotation automatique) en cas d'anomalie ou de dépense imprévue, avec son propre circuit — créé par le service concerné → contrôlé par le N+1 → signé électroniquement par le DG → rattaché à une facture (actions successives simulées sur le même profil Service Achats, comme le reste de l'application qui n'a pas d'authentification réelle par utilisateur). Profils simulés : Service Achats (accès complet) et DFC — Direction Financière et Comptable (vue globale « Factures à valider », virement de crédits, même principe que le contrôle des bulletins de paie du module RH). Les cartes « Clients » et « Fournisseurs » du portail pointent vers `achats/#tiers?type=Client` / `?type=Fournisseur` (filtre préappliqué via le hash).
- `logement/index.html` : module Gestion Locative, regroupant les cartes portail « Locataires » et « Demandeurs » — un dossier de demande attribué devient automatiquement un locataire avec un bail, donc une application unique plutôt que deux silos. L'OPH gère un parc de 100+ lotissements, chacun regroupant un nombre variable de logements ; référentiels : `lotissements` (nom, commune, `lieuDit`, `type` — Locatif social/Accession à la propriété/Mixte/CHE —, cycle de vie `statut` : En projet → En construction → Actif → En réhabilitation, équipements booléens `aireJeux`/`localPoubelle`/`localVelos`/`gardiennage`/`ascenseur`) — cliquer sur un lotissement ouvre sa fiche détail (`openLotissementDetail()`) : identité, équipements, répartition par typologie avec loyer moyen, nombre de logements accessibles PMR (`logements[].pmr`), réhabilitations liées, liste des logements ; `pistesFoncieres` (repérage foncier en amont d'un projet : commune, lieu-dit, surface, nb logements potentiel, statut Repérée/En négociation/Acquise/Abandonnée) ; `projetsConstruction` (opérations de construction pilotées par un chargé d'opération — outil métier « Indigo » de Tahiti Ingénierie côté OPH, non intégré ici —, éventuellement issues d'une piste foncière ou rattachées à un lotissement existant : maître d'œuvre, budget, statut Étude/Financement/Appel d'offres/En construction/Livré) ; `logements`, rattachés à un lotissement (`lotissementId`) et catégorisés (`categorie` : « Logement », « Stationnement » — garages/places de parking également loués par l'OPH — ou « CHE » — hébergement étudiant, avec `capacite` en places pour gérer la colocation) ; `demandeurs`, avec un `typeDemande` (Logement/AAHI/FARE/CHE) qui détermine le parcours d'attribution à l'étape Éligible : Logement suit le workflow Déposée → Instruction → Éligible → Proposée → Attribuée avec proposition d'un logement vacant puis attribution qui crée le locataire et le bail ; AAHI (aide à l'amélioration de l'habitat individuel — subvention de travaux sur le logement déjà occupé par le demandeur) et FARE (maison individuelle en kit posée sur un terrain déjà détenu par le demandeur) passent directement d'Éligible à Attribuée via une attribution qui enregistre le montant/objet des travaux (`d.aahi`) ou le type de fare et l'adresse du terrain (`d.fare`), **sans créer de bail** puisque l'OPH ne gère pas ces biens en location ; CHE (étudiant, hébergement Outumaoro/Paraita) suit Proposée → Attribuée comme un logement classique mais crée un bail annuel (`modeOccupation:"CHE"`, `anneeAcademique`) sur un logement CHE pouvant accueillir plusieurs colocataires simultanés (jusqu'à `capacite` occupants) ; `locataires` ; `baux`, incluant le mode d'occupation (`modeOccupation` : « Location », « Accession à la propriété » — avec `prixVente`, libellés UI adaptés « Mensualité » — ou « CHE ») et l'éligibilité à une aide au logement (`aideType` : AFL/ALE, `aideMontant`) ; `quittances` (génération mensuelle sans doublon, comme la paie du module RH — loyer + refacturation de charges, moins l'aide au logement déduite et conservée en snapshot sur la quittance `aideDeduite`) ; `interventions`, qui couvrent l'entretien de l'ensemble du parc et sont donc rattachées en premier lieu à un `logementId` (tout logement, vacant, occupé ou partie commune), le `bailId` restant optionnel (renseigné uniquement lors d'un signalement par un locataire) ; `rehabilitations` (travaux de réhabilitation par lotissement, éventuellement ciblés sur un logement précis : objet, dates, statut, budget estimé, entreprise). Le moteur de formulaire générique (`FORMS`/`openForm()`) supporte un type de champ `bool` (case à cocher) pour les équipements et l'accessibilité PMR. Profils simulés : Gestion locative (accès complet), Locataire (self-service : bail, quittances, signaler un problème — y compris pour un locataire étudiant CHE) et Demandeur (suivi de son dossier, quel que soit le type de demande). Les cartes « Locataires » et « Demandeurs » du portail pointent vers `logement/#locataires` / `#demandeurs`.
  - Le portail (`index.html`) supporte un `href` explicite par carte (`MODULES.<groupe>[].href`) pour que plusieurs cartes pointent vers des sections différentes d'un même module (fonction `card()`), plutôt que de forcer une correspondance 1 carte = 1 dossier = 1 application.
- Persistance : `localStorage` du navigateur (métadonnées, une clé par module) + `IndexedDB` (contenu des fichiers de la GED) — pas de backend. Chaque module régénère ses propres données de démonstration s'il ne trouve rien en `localStorage` ; le bouton « Reset » du module RH ne réinitialise que ses propres données.
- Déploiement : GitHub Pages, servi automatiquement depuis `main` (aucune étape de build).
- Tests E2E : Playwright (`tests/`, `npm test`) — voir `tests/README.md`. `tests/agent-rh/` couvre le portail self-service agent. `tests/ged.spec.js` couvre le module GED. `tests/achats.spec.js` et `tests/logement.spec.js` couvrent respectivement les modules Achats et Gestion Locative, y compris l'accès depuis les cartes du portail.
